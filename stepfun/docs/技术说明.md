# 一页技术说明 · 端侧知识库（seekdb × 阶跃星辰赛道）

## 1. 模型与量化

**选用模型**：`Xenova/paraphrase-multilingual-MiniLM-L12-v2`（Hugging Face 公开 ONNX 版本，384 维，Apache-2.0）。
选它的原因是中英文混合语料都能编码，且体积适合端侧；备用模型为 `Xenova/all-MiniLM-L6-v2`（同样 384 维），
两者共用同一张表的 `VECTOR(384)` 列，切换模型不需要改表结构。

**量化方案**（运行时由 Transformers.js 的 `dtype` 参数选择，界面可切换）：

| 方案 | dtype | 权重位宽 | 体积（相对 FP32） | 说明 |
| --- | --- | --- | --- | --- |
| FP32 基线 | `fp32` | 32 bit | 1× | 质量基线，用于对照 |
| FP16 | `fp16` | 16 bit | ≈ 1/2 | WebGPU 上带宽更省，精度损失极小 |
| INT8 | `q8` | 8 bit | ≈ 1/4 | 动态量化，每通道缩放因子，CPU/WASM 上更快 |

**体积与压缩比**：页面性能面板在模型加载完成后按实际下载字节数报告体积，导出的 JSON 里字段为
`config.modelSizeMB`。三种精度的实测体积、压缩比与 Recall@5 / nDCG@5 变化见
[`实测记录.md`](./实测记录.md)（数据来自提交应用的实际运行）。

**质量比较方法**：`data/queries.json` 提供 8 条查询及相关文档标注，应用内「运行检索质量评测」
对当前精度配置计算 Recall@5 与 nDCG@5；相同语料、相同查询集、相同后端下横向对比，避免主观判断。

## 2. 端侧运行

**运行时**：Transformers.js 3.7.5（底层 onnxruntime-web），以 ES Module 从 CDN 加载，
模型文件从 Hugging Face 下载后进入浏览器缓存，**推理（包括文档与查询的向量化）全部在用户设备完成**。
页面不包含任何云端推理请求；桥接服务只接收已算好的向量，不做任何模型计算。

**后端选择**：`web/embeddings.js` 的 `detectBackend()` 检测 `navigator.gpu`，优先以
`device: "webgpu"` 初始化；若初始化抛错（驱动缺失、浏览器策略限制等），自动以
`device: "wasm"` 重建，并在顶部徽标显示「已降级」＋实际后端名，性能面板记录 `backend` 字段。

**验证降级路径**：在 Chrome 中通过 `chrome://flags` 关闭 WebGPU（或使用不支持 WebGPU 的浏览器）
重新加载页面，徽标应显示 WASM，检索流程仍完整可用。两种后端的实测数据见实测记录。

## 3. seekdb 使用

**接入方式**：`server/db.mjs` 通过 `@oceanbase/seekdb-node` 在本地启动嵌入式 seekdb 进程
（数据目录 `data/seekdb-data`，`memory_budget=2G`），再用 `mysql2` 走 MySQL 协议执行 SQL。
进程生命周期由桥接服务管理：启动时 `seekdb.open()`，退出时先断连再 `close()`。

**表结构**（知识库 ID 做逻辑分区，单表多库）：

```sql
CREATE TABLE kb_chunks (
  id          VARCHAR(96)  NOT NULL PRIMARY KEY,
  kb_id       VARCHAR(64)  NOT NULL,          -- 知识库/会话隔离
  doc_id      VARCHAR(96)  NOT NULL,          -- 原始文档 ID
  chunk_no    INT          NOT NULL,
  title       VARCHAR(255) NOT NULL,
  content     TEXT         NOT NULL,
  embedding   VECTOR(384)  NOT NULL,
  created_at  TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
  FULLTEXT INDEX idx_fts (content) WITH PARSER ik,
  VECTOR INDEX idx_vec (embedding) WITH (DISTANCE=cosine, TYPE=hnsw, LIB=vsag)
) ORGANIZATION = HEAP;
```

建表时会先尝试 `WITH PARSER ik`（中文分词），若当前版本不支持则自动退回默认解析器，
实际使用的解析器记录在 `/api/health` 与页面徽标的 tooltip 中。

**混合检索**：`mode=hybrid` 时下发单条 SQL，全文匹配负责候选过滤、向量距离负责排序，
由 seekdb 在一次执行计划内完成，前端不做两路结果拼合：

```sql
SELECT id, doc_id, title, content,
       l2_distance(embedding, ?) AS dist,
       MATCH(content) AGAINST(?) AS score
FROM kb_chunks
WHERE kb_id = ? AND MATCH(content) AGAINST(?)
ORDER BY l2_distance(embedding, ?) APPROXIMATE
LIMIT ?;
```

页面「查看本次下发的 SQL」可现场核对实际语句。

**增量写入与索引刷新**：写入走单事务批量 `INSERT ... ON DUPLICATE KEY UPDATE`；
写入完成后立刻调用 `/api/kb/refresh` 并回读计数，确认新增块在刷新后可检索
（seekdb 的 HNSW 为增量索引，不依赖后台重建）。

## 4. 状态与优化

**状态管理**：`kb_id` 作为逻辑知识库边界，清空/统计/检索都带该条件，切换知识库不影响其他库；
前端切换精度或模型时销毁旧 pipeline 并重新加载，避免两个模型同时驻留内存。

**优化点与实测**

1. **批处理**：文档向量化按批（默认 8，可调 1–32）送模型，减少每次调用的固定开销；查询保持单条以压低交互延迟。
2. **冷/热分离**：模型加载后强制执行一次预热推理，把首帧编译成本单独计入 `warmup`，不与后续批处理混淆。
3. **量化**：INT8 把权重压到 1/4，直接减少下载时间与内存占用；FP16 在 WebGPU 上换取带宽收益。
4. **写入批量化**：单事务批量写入替代逐条插入，把写放大与事务开销摊薄。
5. **刷新确认**：写入后显式回读，把「索引刷新」作为独立阶段计时，便于定位增量可见性问题。

各阶段耗时（模型加载、预热、文档向量化、写入、刷新、查询向量化、seekdb 检索、端到端）
在页面「性能实测」表格实时显示，并可导出 JSON，原始数据整理在 [`实测记录.md`](./实测记录.md)。
